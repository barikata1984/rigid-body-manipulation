# 2026-08-06 loaded_dice データセットの wrench 不整合の原因調査

## Topic

下流の質量分布推定で dyn loss が下がらない原因を、データ生成側の 2 つの欠陥として特定した。

## Summary

学習側に渡した `loaded_dice/transforms.json` はノイズ注入版であり、ノイズなし版は同じディレクトリに `unperturbed_transforms.json.bak` として同梱されたまま使われていなかった。再生成は不要で、ファイルの差し替えで足りる。
これとは独立に、`global_gt` が物体座標系、`regressor` がセンサ座標系で書かれる不一致が実在する。ノイズなし版でも座標変換なしでは torque の R² が負になり、変換を施すと force・torque とも R²=0.9999、フレーム対応 300/300 になる。
ノイズ注入そのものではなく振幅が問題であり、`sensors.py` の既定値 (force σ=2 N, torque σ=0.1 N·m) は 2026-07-13/14 に決定済みで未実装の Robotiq FT300-S 公称値 (0.1 N, 0.005 N·m) の 20 倍である。

## History

下流タスクで、`loaded_dice` の dyn loss が epoch 2 以降 `1.37E-02` から動かないという症状が出た。学習側の調査で、この床が「`regressor` の 10 次元列空間内で huber 損失を最小化した理論最適値」と 4 桁一致することが判明し、学習は到達可能な最小値に達しているためデータ側に原因があるという照会文書 `inquiry_2026-08-05_loaded-dice-wrench-inconsistency.md` を受け取った。照会文書は、同一 JSON 内の `regressor` (6×10) と `global_gt` (10) と `wrench` (6) の 3 者だけで閉じた検査により、10 パラメータ最小二乗でも force R²=0.30 / torque R²=0.05、torque 振幅が `regressor @ global_gt` の 2.5–3 倍、`wrench[i]` の最近傍が自フレームになるのは 4/300 と報告していた。対照の hammer は同じ検査で R²≈0.9999 を通る。符号反転・成分順の入れ替え・±25 フレームのシフト・重力列の追加は照会文書の側で棄却済みだった。

残る候補として次の仮説を立てた。

- 摂動 (ノイズ) 注入版のファイルを出荷した
- `wrench` と `regressor` の座標系が食い違っている
- 行の対応が崩れている (記録時の時刻ずれ、書き出し順序の破綻)
- `global_gt` の真値そのものが誤っている
- hammer 生成後の未コミット変更が生成経路を壊した

コード経路の追跡と数値の仮説検定を独立の 2 経路で並行させた。両者は互いの結果を見ずに同じ結論に到達した。

第一の原因は出荷ファイルの取り違えである。学習側が読んだファイルは生成側の `datasets/loaded_dice/spline_20260803_173638_run2/transforms.json` と sha256 が一致し (`058d7569…`)、これは `perturb_wrench=True` (既定値) によるノイズ注入版だった。`recorders/standard_recorder.py:171-173` の命名規則により、摂動版だけが `transforms.json` を名乗り、ノイズなし版は `unperturbed_transforms.json.bak` になる。hammer では生成の約 4 時間後に手作業で `.bak` を外してノイズなし版を昇格させた形跡が出荷先のタイムスタンプに残っているが、loaded_dice ではこの手順が抜けた。学習側は `*.json` しか拾わないため、正しいファイルは同じディレクトリにありながら読まれなかった。

この 1 点で照会文書の症状がすべて定量的に説明できる。摂動版とノイズなし版の差分が実現したノイズそのものであり、その標準偏差は force 1.90/1.91/1.95 N、torque 0.099/0.097/0.098 N·m と、`sensors/sensors.py:24-25` の宣言値 2.0 N / 0.1 N·m に対し χ² 検定で区別できない (Holm 補正後 p はすべて 1.0000)。loaded_dice の torque 信号 RMS は 0.023–0.033 N·m しかないため、σ=0.1 N·m のノイズが信号を覆い、ノイズ込みで予測した torque RMS は観測と 1–4% で一致する。照会文書 §2 の「慣性テンソルまたはモーメントアームが `global_gt` より大きい物体で生成された」という推論は成り立たず、正しい読みは torque チャンネルの信号対雑音比が約 0.3 ということである。§4 の 4/300 も行ずれではない。`simulators/simulator.py:184-197` の 1 ステップ内で `wrench` と `twist`/`dtwist`/`regressor` は同一 `MjData` から `mj_step` の前に取得され、7 本のリストを `zip(*containers, strict=True)` で束ねるため、構造上ずれない。滑らかな軌道に宣言値どおりの独立同分布ガウスノイズを載せた帰無モデルを 100–200 回複製したところ、最近傍一致は 8.4±2.8 件 (観測 4 件は経験的 p=0.070)、Hungarian で force だけ改善し torque は改善しないという非対称まで再現した。最小二乗質量が 0.61 倍に縮むのは、`regressor` 自体も関節量のノイズで独立に摂動されているためで (qacc のノイズ倍率は √6·fps²、`dtwist_sen` の並進成分はノイズ std 4.25 が信号 RMS 3.69 を上回る)、教科書どおりの説明変数誤差による縮小推定である。hammer の摂動版でも同じ 0.63 倍が出た。

第二の原因は座標系の不一致で、こちらは実在するバグである。`global_gt` は `xml_models/targets/loaded_dice/object_cad_gt.csv` の CAD 真値を物体 (aabb) 座標系原点まわりへ平行軸移動した値であり (CSV との相対差は全 10 成分で 0.000e+00)、一方 `regressor` はセンサ座標系で組まれる。両者は `pose_sen_obj` = diag(−1,−1,1) で関係し、変換は `mx, my, iyz, izx` の符号反転に相当する。ノイズなし版で変換の有無を比べると force 残差 0.4105 → 0.0179 N、torque 残差 0.0536 → 0.00026 N·m、フレーム対応 300/300 となり、torque の R² は負値から +0.9999 に変わる。この数値はメインループでも出荷ファイルに対して直接再計算して確認した。hammer でこのバグが見えなかったのは重心が z 軸上にあり慣性テンソルがほぼ対角で、反転対象の 4 成分がすべて 1e-9 以下だからである。重心が軸から外れた最初の物体である loaded_dice で初めて露呈した。未コミット変更の `main.py:126-127` は `ls`/`tls` だけをセンサ系から物体系へ揃えており、`global_gt` 側は手つかずのまま残っていた。

残る仮説はいずれも棄却された。座標系の取り違えを `wrench` 側に求める仮説は、`pose_sen_obj` と `transform_matrix` による回転・随伴変換の全 11 変種で残差が基準より悪化したことで棄却した。行の対応の破綻は上記の帰無モデルで棄却した。真値の誤りは CSV との厳密一致で棄却した。生成コードの退行は、未コミット差分 112 行の全文精査により `wrench`/`twist`/`dtwist`/`regressor` の計算に触れる変更がゼロであることを確認して棄却した (差分は慣性パラメータ変換関数の追加、`ls`/`tls` の座標系変換、`labels` からの `aabb_scale` 削除、マスク生成、描画設定である)。ついでに、保存済み `regressor` が `twist_sen`/`dtwist_sen` から解析的に再構成した Newton–Euler 回帰子と計算機精度 (relRMS 1e-18) で一致することも確認され、不整合を持つ要素が `wrench` だけであることが確定した。

ノイズ振幅そのものについては、既に判断が済んで実装されていない項目に行き当たった。`sensors/sensors.py` の既定値 force σ=2 N / torque σ=0.1 N·m は、2026-07-13/14 に Robotiq FT300-S の公称値 (0.1 N / 0.005 N·m) へ変更すると決定されながらコード変更が未実施のまま残っていたもので、公称値のちょうど 20 倍である。公称値であれば loaded_dice の torque 信号対雑音比は約 6 になり、摂動版でも同定に耐えうる。つまり摂動版が学習に使えなかったのはノイズを注入したこと自体ではなく、実機グラウンディングを経ていない既定値が過大だったことによる。運動学側の qacc ノイズ過大は 2026-07-12 起票の未解決課題としてそのまま残る。

対処は 4 件を提案したが、いずれもこのセッションでは実施していない。出荷先の `transforms.json` を同梱の `unperturbed_*.json.bak` に差し替えること、`global_gt` をセンサ系へ変換してから書き出すこと (`transfer_iparams` が既にある)、摂動版だけが正名を取る命名規則を見直すこと、乱数種の固定と生成時設定のスナップショット書き出しを入れることである。最後の 2 件は追跡可能性の問題として現れた。生成コマンドはシェル履歴にもデータセット内にも残っておらず (`config_export_path` の既定が `None`)、`sensors/sensors.py:32` の `default_rng()` は種を指定していないため摂動系列は原理的に再現できない。

照会文書が提案した出荷前チェック `‖regressor @ global_gt − wrench‖ / ‖wrench‖ < 1e-2` はそのままでは採用できない。`global_gt` を座標変換せずに使うと正しい loaded_dice のファイルを force 0.2168 で誤って弾き、hammer の正ファイルも torque 0.0159 で僅差不合格になる。座標変換を適用したうえで torque の閾値を 2e-2 程度に緩める必要がある。

付随して、照会文書が hammer を「実機」データとしている点に疑いが出た。出荷先ディレクトリの中身 (`tracking_qpos.png`、`tracking_acc_ft.png`、`transforms_*.json.bak` 群) が本リポジトリのシミュレータ出力の構成と一致する。根拠はディレクトリ構成のみで確証はないが、対照実験の解釈に関わるため提供元への確認が要る。

## Decisions

- loaded_dice は再生成せず、出荷先に同梱済みの `unperturbed_transforms.json.bak` への差し替えで対処する / 却下: データセットの再生成 — エージェント判断 (未実施)
- 照会文書 §2 (慣性・モーメントアーム過大) と §4 (フレーム対応の破綻) の推論は取り下げ、いずれもノイズ振幅で説明する — エージェント判断
- 出荷前チェックは `global_gt` をセンサ系へ変換したうえで torque 閾値 2e-2 として採用する / 却下: 照会文書の原案 (変換なし・両ブロック 1e-2) — エージェント判断 (未実施)
